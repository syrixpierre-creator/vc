# Security model

## Principles
- **Never collected**: Google passwords, PINs, recovery phrases, private keys, card numbers or CVVs, Telegram/WhatsApp credentials. The payout form rejects a value that looks like a 12–24-word recovery phrase (`looks_like_secret`), and every form that could tempt someone to paste a secret says not to.
- **Contacts belong to their owner.** Every contact query is scoped by the owner's ID in SQL. Admin endpoints return counts and sync state, never names, numbers or e-mails of contacts. Reports and logs never contain contact data.
- **The database is the source of truth.** Money and progress are derived from append-only tables; Redis only carries queue wake-ups.

## Authentication
- Google OpenID Connect only, with PKCE (S256), a random `state` bound to the browser by a `__Host-oauth` cookie (10 minutes, single use) and a `nonce` checked in the ID token. ID tokens are verified locally (RS256 against Google's JWKS, issuer, audience, expiry; `alg: none`/HS256 rejected). Unverified Google e-mails cannot sign in.
- Users are identified by the Google subject (`sub`), not the e-mail. The admin bootstrap matches `ADMIN_EMAIL` against the **verified** identity at first sign-in and then pins the subject.
- Sessions: 256-bit random IDs, stored only as SHA-256 hashes, `__Host-sid` cookie (`Secure`, `HttpOnly`, `SameSite=Lax`), rotated daily, 14-day idle / 30-day absolute expiry, revocable per device; all sessions revoked on suspension.
- Google Contacts uses a separate, incremental consent; tokens are bound to the signed-in user and to the same Google account.

## Requests
- CSRF: per-session token in a header for every state-changing request, plus an `Origin` check.
- Every route declares its access level (`public`, `user`, `write`, or a permission). The router enforces it before the handler runs; the OpenAPI document is generated from the same declarations.
- Input: strict JSON parsing with unknown-field rejection (mass assignment), length limits, typed validators; VCF parser with size, card and line limits and formula-injection-safe CSV exports.
- Rate limits per IP and per user (Redis sliding window; falls back to allowing requests if Redis is down rather than locking everyone out — the database constraints still prevent abuse of money paths).
- Pages: strict Content-Security-Policy (`script-src 'self'`, `style-src 'self'`, no inline code, `frame-ancestors 'none'`, `object-src 'none'`), `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`, HSTS (Caddy). The front end never uses `innerHTML`: user text is always inserted as text.

## Data at rest
- AES-256-GCM with versioned keys (`ENCRYPTION_KEY`, `ENCRYPTION_KEY_VERSION`, `ENCRYPTION_KEYS_PREVIOUS` for rotation) for OAuth tokens, payout details and users' contact backups. The ciphertext is bound to its record (associated data), so it cannot be copied to another user.
- Database backups are encrypted with `BACKUP_PASSPHRASE` before they leave PostgreSQL's container.
- Security events store a truncated network prefix and a keyed hash, never full IP addresses.

## Money paths
- Integer cents; append-only ledger enforced by database triggers; idempotency keys on every credit; per-user advisory locks around payouts and reward creation; at most one open payout per user (database constraint); payouts marked paid only with a reference and an explicit confirmation; recipient details frozen at request time and revealed to staff only through an audited action.

## Roles (least privilege)
`super_admin`, `user_manager`, `finance_manager`, `challenge_manager`, `support_agent`, `auditor`. Each admin action checks a permission on the server and writes an audit record (who, what, before/after, reason); the audit table refuses UPDATE and DELETE.

## Infrastructure
Only Caddy is reachable from the internet. PostgreSQL and Redis sit on an internal Docker network with no published ports and no internet route; Redis requires a password. App and worker containers are read-only, non-root, without capabilities. Secrets live only in `.env` (mode 600, git-ignored) and are generated by the installer.

## Rotating secrets
- `SESSION_SECRET`: change it and restart; everyone signs in again.
- `ENCRYPTION_KEY`: set the new key, increase `ENCRYPTION_KEY_VERSION`, put the old one in `ENCRYPTION_KEYS_PREVIOUS` (`1:<hex>`), restart. Old data stays readable; new writes use the new key.
- Google client secret: create a new secret in the console, update `.env`, restart, delete the old secret.
- Database/Redis passwords: change in `.env` and in the service (`ALTER USER syrix PASSWORD ...`), then `docker compose up -d`.

## Reporting a vulnerability
E-mail `syrixcompany@gmail.com` with the details. Please do not test against other people's accounts.

## Verified vs not verified
Verified by automated tests (194 server tests on a real PostgreSQL, 10 browser end-to-end flows): the rules above for sessions, CSRF, access control, ownership, money, input handling and headers. **Not done**: an external penetration test, a dependency SBOM review beyond `npm audit` (0 known vulnerabilities at release), and a review of the real Google round trip.
